# ADR-0002 — PostgreSQL with Drizzle ORM and hand-reviewed SQL migrations

**Status:** Accepted · **Date:** 2026-09-10 · **Approved:** 2026-09-10

## Context
The data model needs row-level security (tenant isolation), declarative partitioning
(analytics facts), full-text and trigram search, `jsonb` with GIN, window functions and
CTEs (attribution and funnel queries), and `SET LOCAL` per transaction under a connection
pooler. The ORM must not obstruct any of these.

## Decision
PostgreSQL 16+ as the single system of record. **Drizzle ORM** (0.45.2) for typed queries,
confined to `infrastructure/` layers. Migrations are checked-in SQL, generated by
`drizzle-kit` and reviewed by a human; RLS, partitioning and concurrent index work is
hand-written.

## Alternatives considered
- **Prisma.** Rejected: its `latest` currently points at an 8.0 release candidate
  (mid-major churn), and RLS, `SET LOCAL`, partitioned tables and complex analytical SQL
  remain the areas where it fights hardest.
- **Raw SQL only.** Rejected: loses compile-time safety across a large schema.
- **Kysely.** Viable and close; Drizzle chosen for schema-definition ergonomics and
  migration generation.

## Consequences
**Positive:** no capability of Postgres is out of reach; migrations are reviewable as
security artefacts; no query engine binary in the deployment.

**Negative:** Drizzle is pre-1.0 and may introduce breaking changes; its ecosystem is
smaller than Prisma's; developers must know SQL — which we treat as a requirement, not a
cost.

**Mitigation:** no Drizzle type appears in a domain, contract or application signature, so
replacement is confined to repository internals. Migrations, being SQL, are unaffected by
any ORM change.
